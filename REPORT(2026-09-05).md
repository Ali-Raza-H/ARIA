# ARIA Feature, Issue, and Product Roadmap Report

**Date:** September 5, 2026  
**Project:** ARIA — Adaptive Reasoning and Intelligence Assistant  
**Status:** Architecture and product audit

---

## 1. Executive Summary

ARIA is currently a capable terminal-based LLM assistant with multi-provider support, custom and native tool calling, an independent coding agent, LifeOS connectivity, optional speech, a Rich terminal UI, logging, and a growing test suite.

It is **not yet a full daily-life assistant**. The largest gaps are not additional model providers; they are persistent memory, scheduling, background execution, permissions, context management, proactive workflows, integrations, and safety controls.

The recommended strategy is to evolve ARIA in this order:

1. **Safety and reliability** — permissions, confirmations, retries, context limits, rollback, and provider health checks.
2. **Personal assistant fundamentals** — durable memory, user profile, reminders, scheduling, background jobs, and notifications.
3. **Daily-life integrations** — calendar, email, tasks, notes, contacts, web research, and messaging.
4. **Multimodal interaction** — speech input, voice conversations, documents, images, and optional screen context.
5. **Proactive intelligence** — briefings, follow-ups, goal tracking, routine detection, and autonomous workflows with explicit user control.

- Native tool calling for compatible providers/models.

## 3. Known Issues and Weaknesses

## 3.1 Critical product gaps

### A. Memory is ephemeral

Current session memory is deleted when the session exits. ARIA cannot reliably remember user-approved information across launches.

Missing:

- Persistent user profile.
- Long-term facts and preferences.
- Important people and relationships.
- Recurring routines.
- Goals and commitments.
- Searchable memories.
- Memory importance and expiration.
- User controls to inspect, edit, export, or delete memories.
- Encryption or stronger protection for sensitive memories.

Impact: ARIA behaves more like a fresh chatbot than a continuously useful personal assistant.

### B. No native reminder scheduler

The system has LifeOS calendar/task support but no local scheduler or background reminder engine.

Unsupported experiences include:

- “Remind me in 30 minutes.”
- “Remind me every weekday at 8 AM.”
- “Tell me two days before this deadline.”
- “Follow up with me if I have not completed this task.”
- “Give me a morning briefing every day.”

Impact: ARIA cannot proactively help when the user is away from the terminal.

### C. No background job architecture

LLM calls, coder deployments, and speech playback are synchronous. Long operations block the REPL.

Missing:

- Background task queue.
- Job IDs.
- Job status tracking.
- Cancellation.
- Retry policies.
- Persistent jobs across restarts.
- Notification delivery.
- Concurrent but controlled work.

Impact: ARIA cannot reliably run scheduled or long-lived assistant workflows.

### D. Dangerous actions have no approval policy

ARIA can run shell commands, write files, modify files, and perform LifeOS writes without a structured permission layer.

Risky actions include:

- Deleting or overwriting files.
- Installing packages.
- Running arbitrary shell commands.
- Changing configuration.
- Creating or modifying LifeOS records.
- Updating finance, health, or calendar data.
- Autonomous coding-agent edits.
- External network requests.

Impact: The current architecture is unsuitable for unattended autonomy.

### E. Context grows without token-aware compaction

The full conversation and tool history remain in session memory. There is no token counting, summarization, or retrieval strategy.

Likely failures:

- Context-window exhaustion.
- Increasing latency and cost.
- The model forgetting tool rules.
- Lower-quality responses after long sessions.
- Oversized tool results dominating the conversation.

### F. No web research/browser tools

ARIA cannot perform reliable current-information research, cite sources, monitor pages, or work with online documents.

Missing capabilities:

- Search.
- Fetch and parse webpages.
- Citation tracking.
- Current news and product research.
- Price or availability monitoring.
- Webpage change detection.
- Prompt-injection defenses for external content.

## 3.2 Reliability issues

### A. Provider capability handling is incomplete

Provider behavior varies by model, but capabilities are not represented explicitly.

Needed capability flags include:

```yaml
capabilities:
  native_tools: false
  streaming: true
  vision: false
  structured_output: false
  audio_input: false
```

The system should select native tools, custom tools, or a compatibility mode automatically.

### B. Provider fallback is missing

If a provider fails, ARIA does not automatically switch to another configured model/provider.

Needed:

- Primary provider.
- Secondary provider.
- Per-task fallback policy.
- Retryable versus non-retryable error classification.
- User-visible fallback notifications.
- Circuit breakers for repeatedly failing providers.

### C. LLM request controls are limited

Per-provider settings should include:

- Request timeout.
- Maximum retries.
- Backoff policy.
- Temperature.
- Maximum output tokens.
- Context/token limits.
- Optional reasoning budget.
- Rate-limit handling.

### D. Runtime configuration changes are not persisted

Changes made using commands such as `/provider`, `/model`, `/workspace`, `/tts`, and `/iterations` disappear after restart.

Suggested commands:

```text
/config show
/config save
/config reset
```

Runtime changes should be saved only after explicit user approval.

### E. Tool results need stronger size and privacy controls

Some tools can return large file contents or large search outputs. Sensitive content may also enter model context or logs.

Needed:

- Per-tool output limits.
- Binary-file detection.
- Secret scanning before model submission.
- PII redaction options.
- User-visible truncation indicators.
- Configurable sensitive directories.
- Better handling of symlinks and special files.

### F. Coding agent lacks checkpoints and rollback

The coder agent can modify multiple files, but there is no automatic snapshot, git checkpoint, or rollback mechanism.

Needed:

- Pre-deployment workspace status.
- Optional automatic git branch/checkpoint.
- Changed-file manifest.
- Patch preview.
- Approval before applying risky changes.
- Rollback command.
- Post-change test report.

### G. Session memory lifecycle needs improvement

Current session files are ephemeral, but interrupted/crashed processes may leave files behind. There is no cleanup daemon, retention policy, or recovery flow.

Needed:

- Session expiration.
- Startup cleanup.
- Crash recovery.
- Session listing.
- Resume previous session.
- Explicit secure deletion policy.

## 3.3 Assistant-quality weaknesses

### A. The system prompt is not a complete personal-assistant operating model

ARIA has a persona and general behavioral rules, but it lacks structured policies for:

- Planning and prioritization.
- Clarifying ambiguous requests.
- Tracking commitments.
- Deciding when to ask permission.
- Deciding when to use LifeOS.
- Handling uncertainty.
- Reporting completed versus planned work.
- Managing recurring routines.
- Proactively identifying conflicts.

### B. No structured task state

Tasks are mostly represented as conversational text or delegated tool calls. There is no unified internal task model with states such as:

```text
proposed -> approved -> scheduled -> running -> blocked -> completed -> archived
```

### C. No user profile

The constructor has a user name parameter, but there is no complete profile system for:

- Name and pronouns.
- Time zone.
- Location.
- Working hours.
- Preferred communication style.
- Calendar preferences.
- Health or accessibility preferences.
- Notification preferences.
- Privacy preferences.

### D. No time-zone or locale model

A daily assistant must understand:

- User time zone.
- Daylight saving changes.
- Locale and date formatting.
- Working days.
- Holidays.
- Travel or temporary location.

### E. No proactive behavior

ARIA waits for a user message. It does not currently produce:

- Morning briefings.
- Evening reviews.
- Deadline warnings.
- Calendar conflict alerts.
- Task follow-ups.
- Goal progress updates.
- Routine reminders.
- Important-news alerts.

### F. Speech is output-only

There is no speech-to-text, wake word, voice interruption, or conversational voice mode.

## 4. Missing Features to Add

## 4.1 Safety and permissions

Implement a policy engine with action categories:

| Category | Examples | Default behavior |
|---|---|---|
| Read-only | Read files, list tasks, inspect calendar | Allow |
| Low-risk write | Create a note, create a draft | Ask once or allow by setting |
| High-risk write | Delete files, modify finance/health data | Always ask |
| External communication | Send email/message, publish content | Always ask |
| Destructive/system | Shell commands, package install, bulk edits | Ask with preview |
| Unattended | Scheduled actions | Require explicit recurring approval |

Every approval should show:

- Action.
- Target.
- Data being sent.
- Files or records affected.
- Reversibility.
- Expiration of approval.

## 4.2 Persistent memory

Add a memory subsystem with:

- SQLite as the initial durable store.
- Memory categories.
- Importance score.
- Source conversation and timestamp.
- Confidence.
- Expiration date.
- User-approved versus inferred state.
- Full-text search.
- Optional embeddings later.
- Encryption or OS keyring integration.
- `/remember`, `/forget`, `/memories`, `/memory export` commands.

Suggested record:

```json
{
  "id": "memory-123",
  "kind": "preference",
  "content": "The user prefers concise answers.",
  "source": "user_explicit",
  "confidence": 1.0,
  "importance": 0.8,
  "created_at": "2026-09-05T10:00:00Z",
  "expires_at": null
}
```

## 4.3 Scheduling and reminders

Add a scheduler abstraction supporting:

- One-time reminders.
- Recurring schedules.
- Relative durations.
- Calendar-linked reminders.
- Task-deadline reminders.
- Time-zone-aware execution.
- Snooze.
- Completion and dismissal.
- Quiet hours.
- Notification channels.

Suggested commands:

```text
/reminders
/remind me in 30 minutes to stretch
/remind me every weekday at 08:00 to review priorities
/snooze <id> 15m
/dismiss <id>
```

## 4.4 Background jobs

Create a job manager with:

- Job ID.
- Job type.
- Status.
- Progress.
- Created/started/completed timestamps.
- Retry count.
- Cancellation state.
- Result/error.
- Permission context.
- Persistent storage.

Suggested commands:

```text
/jobs
/job <id>
/cancel <id>
```

## 5. Prioritized Roadmap

## Phase 0 — Stabilization

### Goals

Make the current assistant safe and predictable before adding autonomy.

### Work

- Add provider health checks.
- Add per-provider timeouts and retries.
- Add provider fallback configuration.
- Add native/custom capability metadata.
- Add context-size measurement.
- Add tool-output limits.
- Add command cancellation where possible.
- Add coder workspace checkpoint/rollback.
- Add session cleanup and resume behavior.
- Validate all example configuration files in CI.
- Add mocked HTTP tests for every provider adapter.
- Add a `/health` command.
- Add a `/usage` command.

### Exit criteria

- A failed provider does not terminate the assistant.
- A long or malformed tool result cannot exhaust the context unexpectedly.
- Coder changes can be reviewed and rolled back.
- All documented config examples parse successfully.

## Phase 1 — Personal foundation

### Goals

Give ARIA persistent identity and reliable user-approved memory.

### Work

- Add SQLite-backed memory.
- Add user profile.
- Add memory commands.
- Add time-zone configuration.
- Add privacy settings.
- Add retention and deletion controls.
- Add context summarization and memory retrieval.

### Exit criteria

- ARIA remembers approved facts after restart.
- The user can inspect and delete every stored memory.
- Sensitive memory is not written to logs.
- Long conversations remain usable.

## Phase 2 — Scheduling and proactive assistance

### Goals

Allow ARIA to help without waiting for a prompt.

### Work

- Add scheduler.
- Add persistent background jobs.
- Add reminders.
- Add desktop notifications.
- Add quiet hours.
- Add morning and evening briefing workflows.
- Add task follow-up logic.

### Exit criteria

- A reminder survives restart.
- Jobs expose status and can be cancelled.
- Notifications respect time zone and quiet hours.
- Every unattended action has an explicit permission record.

## Phase 3 — Daily-life integrations

### Goals

Connect ARIA to the user’s real information and communication systems.

### Work

- Calendar connectors.
- Email connector.
- Messaging connector.
- Contacts and relationship tracking.
- Web research.
- Personal notes and document indexing.
- LifeOS synchronization and conflict handling.

### Exit criteria

- ARIA can produce a trustworthy daily briefing.
- External communication is draft-first and approval-gated.
- Calendar changes are conflict-aware.
- Sources are cited for web research.

## Phase 4 — Multimodal interaction

### Goals

Make ARIA usable beyond text input.

### Work

- Speech-to-text.
- Push-to-talk.
- Streaming TTS.
- Image and PDF understanding.
- Document search.
- Optional screen/camera context.

### Exit criteria

- Voice input/output works without blocking core assistant tasks.
- Users can interrupt speech.
- Document answers include page/source references.

## Phase 5 — Controlled autonomy

### Goals

Allow ARIA to perform useful proactive work while preserving user control.

### Work

- Routine detection.
- Goal monitoring.
- Deadline risk detection.
- Follow-up suggestions.
- Autonomous workflows.
- Approval templates.
- Per-domain autonomy budgets.
- Audit trails.

### Exit criteria

- The user can define exactly what ARIA may do unattended.
- Every autonomous action is logged and reversible where possible.
- ARIA explains why it acted and what it changed.

## 7. Security and Privacy Requirements

Before adding proactive or communication features, ARIA should implement:

- No secrets in prompts or logs.
- Secret redaction before tool results enter memory.
- Least-privilege integration credentials.
- Explicit permission scopes.
- Approval for external communication.
- Safe handling of untrusted web content.
- Prompt-injection isolation for retrieved content.
- Workspace sandboxing.
- Optional read-only mode.
- Audit log for external side effects.
- Encryption or OS-protected storage for personal memory.
- Data export and complete deletion.
- Clear indication when an action is simulated, drafted, queued, or completed.

## 8. Product Definition of a Full-Blown Daily Assistant

ARIA should eventually be able to:

1. Know the user’s preferences without repeatedly asking.
2. Remember important facts across sessions with user control.
3. Understand the current date, time zone, schedule, and priorities.
4. Summarize the day and identify conflicts.
5. Manage tasks, goals, habits, notes, and calendar events.
6. Set reminders that survive restarts.
7. Run background jobs and report progress.
8. Research current information with citations.
9. Draft emails and messages without sending them unexpectedly.
10. Ask for approval before consequential actions.
11. Work through voice, text, documents, and images.
12. Delegate complex coding/system work safely.
13. Recover from provider failures.
14. Explain what it knows, what it inferred, and what it actually did.
15. Be useful proactively without becoming unpredictable or intrusive.

The central product principle should be:

> **ARIA may be proactive, but never silently consequential.**
