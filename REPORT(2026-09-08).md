# ARIA Implementation and Capability Audit

**Report date:** 2026-09-08  
**Repository:** ARIA — Adaptive Reasoning and Intelligence Assistant  
**Scope:** Current repository state, including the Playwright browser and Hyprland desktop-control additions made for this request.

## 1. Executive summary

ARIA is a modular Python 3.11 terminal assistant with:

- Multiple hosted OpenAI-compatible providers and local Ollama.
- A conversational agent loop with native and custom `<tool_call>` routing.
- A separate coding agent with its own provider session and iteration budget.
- Workspace-scoped filesystem tools and shell execution.
- Local SearXNG research with extraction, caching, retry limits, source IDs, and SSRF-oriented URL checks.
- SQLite/Chroma persistent memory with retrieval, summarization, promotion, retention, and wipe operations.
- Optional speech backends and two terminal UI backends.
- New ARIA-only persistent Playwright browser tools.
- New ARIA-only Hyprland desktop tools with configurable managed/unrestricted modes.

The architecture is a good modular starting point, but the system is currently closer to a powerful single-user prototype than a hardened autonomous-computer agent. The largest risks are not syntax errors: they are permission design, prompt/tool correctness, unbounded or poorly measured context growth, credentials and persistent browser state, arbitrary shell access, lack of action confirmation, and insufficient end-to-end testing against real provider/Wayland/browser behavior.

### Overall assessment

| Area | Assessment |
|---|---|
| Modularity | Good; tools, providers, memory, UI, and agents are separated. |
| Basic test coverage | Good for core pure logic and fakes; weaker for live integrations. |
| Provider portability | Useful abstraction, but normalized usage/context metadata is missing. |
| Browser control | Implemented and opt-in; requires Chromium installation and live validation. |
| Desktop control | Implemented and opt-in; managed mode is safer than unrestricted mode. |
| Security posture | Adequate for a trusted local prototype; not adequate for hostile prompts or unattended autonomy. |
| Token/cost observability | Currently mostly estimates; provider usage is not normalized or persisted. |
| Production readiness | Not ready for unattended full-computer control. |

Available tools when `browser.enabled: true`:

- `browser_navigate`
- `browser_snapshot`
- `browser_tabs`
- `browser_new_tab`
- `browser_select_tab`
- `browser_close_tab`
- `browser_click`
- `browser_type`
- `browser_press`
- `browser_screenshot`
- `browser_download`
- `browser_upload`

The service uses a persistent Chromium context, so cookies and login state can survive ARIA restarts. The browser profile is configurable and defaults to `data/browser-profile`. Playwright is a normal project dependency; Chromium itself must be installed separately:

```bash
uv sync
uv run playwright install chromium
```

The browser tools are registered in ARIA's registry only. The independent coder registry does not receive them.

### 2.2 Hyprland and desktop capability

Added `src/aria/tools/desktop.py` and configuration under `desktop:`.

Inspection tools:

- `desktop_monitors`
- `desktop_workspaces`
- `desktop_clients`
- `desktop_active_window`
- `desktop_keybinds`
- `desktop_screenshot`

Managed actions:

- `desktop_dispatch` with an allow-list of common window/workspace actions.
- `desktop_launch` using named command arrays from `desktop.launchers`.
- `desktop_input` for type/key/click/move using the selected input backend.

Unrestricted-only actions:

- `desktop_raw_dispatch` for arbitrary `hyprctl dispatch` arguments.
- `desktop_set_keybind` for marked keybind changes followed by `hyprctl reload`.
- `desktop_exec` for named configured commands.
- `desktop_shell` for arbitrary shell commands.

The configured input backends are:

- `arch`: `wtype`, `ydotool`, and `grim` by default.
- `pyautogui`: lazy-loaded Python fallback, installed with `uv sync --extra desktop`.

The requested default is represented as `desktop.mode: managed`; desktop capability itself remains opt-in with `desktop.enabled: false` in the example configuration. This prevents a default ARIA launch from controlling the machine before the feature is deliberately enabled.

## 3. Existing architecture review

### 3.1 Agent loop

`BaseAgent` coordinates:

1. Memory preparation.
2. User-message insertion.
3. Provider completion.
4. Native tool calls and custom text-protocol calls.
5. Tool execution through `ToolRegistry`.
6. Tool-result insertion.
7. Repeated model rounds until completion or the iteration limit.

This is conceptually straightforward and provider-neutral. The separate `CoderService` prevents heavy coding context from directly polluting ARIA's normal conversation, which is a sound design decision.

The custom tool protocol is useful for Ollama models that do not support native tools, but it creates a second protocol path that must remain behaviorally equivalent to native function calling. It also increases prompt size and failure modes.

### 3.2 Tool registry

The registry provides a clean contract:

- Tool name.
- Provider-neutral JSON schema.
- Callable handler.
- Consistent error conversion.
- Per-call logging.

The registry catches exceptions and returns them to the model rather than killing the conversation. That improves resilience, but returning raw exception type/message strings can reveal local paths, command details, or implementation internals.

### 3.3 Filesystem and shell

Filesystem paths are resolved and constrained to the configured workspace. This is an important boundary.

The normal shell tool executes through the operating system shell in the workspace. Therefore, ARIA already has a broad local execution capability even before desktop tools are enabled. The new managed desktop layer does not eliminate this existing power. A hostile or confused model can potentially use the existing shell tool for desktop-affecting commands unless tool exposure or command policy is tightened.

### 3.4 Web research

The existing SearXNG layer is stronger than a minimal web-search implementation:

- Bounded search/page call counts.
- Caching.
- Retry logic.
- Concurrent page fetch limiting.
- Source identifiers.
- Public URL validation and explicit host exceptions.
- Extracted readable text.
- Prompt guidance that external content is untrusted.

The new Playwright browser is intentionally separate from this research layer because a browser can retain state and perform mutations. That separation is good, but the system prompt should make the distinction even more explicit: research tools are evidence retrieval; browser tools are real-world interaction.

### 3.5 Persistent memory

The hybrid memory design is ambitious and useful: structured facts in SQLite, semantic retrieval in Chroma, and chat history in a separate collection. Retention and explicit wipe commands are positive features.

The main concern is complexity. Memory has multiple asynchronous/background behaviors, LLM summarization, embeddings, promotion logic, ranking, and lifecycle management. Every added layer increases consistency and observability requirements. A future abstraction should expose one tested memory interface and hide storage-specific details from the agent/UI.

### 3.6 UI and chain-of-thought display

The two UIs and event stream provide good operational visibility. However, the current wording and behavior call the displayed events “chain of thought.” Tool calls, tool results, rounds, and streamed response text are useful execution traces, but they are not a faithful or safe representation of private model reasoning. The product should rename this to something like **execution trace** or **work log** and avoid encouraging models to reveal hidden reasoning.

## 4. Verified defects and implementation concerns

### 4.1 New browser implementation concerns

1. **Persistent credentials are high impact.** A persistent profile means a model action can operate on logged-in accounts. The profile must never be shared with a normal interactive browser process, and it should be backed up or deleted intentionally.
2. **No confirmation layer exists.** This matches the explicit requested policy, but it means clicks, typing, downloads, uploads, and submissions can happen autonomously.
3. **Navigation allows `file:` URLs.** This is useful for local work, but it means browser pages can read local files when the browser permits it. A future policy should make local navigation separately configurable.
4. **Downloads and uploads are filesystem mutations.** They currently resolve relative paths against the workspace but do not implement quotas, extension policies, malware scanning, or a dedicated download directory.
5. **Selectors are model-supplied.** CSS/text selectors can be brittle and can target unintended elements. A stronger interface would first return a structured accessibility snapshot with stable element references.
6. **Only one active page is tracked.** Tabs can be listed and selected, but there is no navigation history abstraction, popup policy, or explicit handling of pages opened by a click.
7. **No browser context hardening is configured.** There is no explicit permission denial policy for geolocation, notifications, camera, microphone, clipboard, or downloads.
8. **No live browser test is present.** The service was tested only at the path/configuration level in this pass; Chromium launch, page navigation, downloads, uploads, and Wayland-visible browser behavior still need an integration test on the target machine.

### 4.2 New desktop implementation concerns

1. **Unrestricted mode is genuinely unrestricted.** `desktop_shell` uses `shell=True`, and `desktop_raw_dispatch` accepts arbitrary dispatcher arguments. This is intentional for the requested power mode but should never be enabled for an untrusted model or unattended process.
2. **The existing normal shell tool remains broad.** Even with `desktop.mode: managed`, ARIA's ordinary shell tool can affect the desktop. Managed desktop mode is therefore not a complete sandbox.
3. **No confirmation layer exists.** The user explicitly selected no extra prompts. This creates risk around closing windows, sending keystrokes, launching applications, changing workspaces, editing keybinds, and interacting with sensitive windows.
4. **Wayland utility behavior is environment-dependent.** `ydotool` may require `ydotoold` and appropriate device permissions; `wtype` and screenshot tools depend on session configuration. This cannot be fully verified from a static test.
5. **Input coordinate limits are generic.** The current 0–10000 range is a validation bound, not a monitor-aware coordinate model. Multi-monitor layouts and scaling may require normalized or monitor-specific coordinates.
6. **`desktop_set_keybind` edits text heuristically.** It only updates lines marked with `ARIA_BIND`; it does not parse Hyprland configuration syntax, includes, variables, submaps, or duplicate semantics.
7. **Keybind inspection is version-sensitive.** `hyprctl -j binds` behavior may differ across Hyprland versions and should be tested on the actual installation.
8. **Launchers are command arrays but not policy-rich.** A configured launcher can still start a powerful process. There are no environment restrictions, process ownership checks, or lifecycle tracking.
9. **Desktop screenshots can expose secrets.** Screenshots may contain passwords, messages, tokens, financial information, or private documents. They need retention and redaction policies.

### 4.3 Existing architectural concerns

1. **Provider API differences are under-modeled.** The `Provider` protocol returns only content and normalized tool calls. It does not return usage, finish reason, context limit, request id, latency, or retry information.
2. **Ollama and hosted adapters have different streaming/tool semantics.** The custom protocol fallback is useful but makes complete equivalence difficult to guarantee.
3. **Context compaction is character-based.** `_messages_for_provider` uses an 80,000-character budget, which is only an approximation and can be badly wrong for code, JSON, non-English text, or provider-specific tokenization.
4. **Memory context and conversation context can compete.** Retrieved memory is injected into the system prompt, while historical tool payloads can also remain in the conversation. This can duplicate information and increase cost.
5. **Tool results can be large.** Web pages, shell output, screenshots represented as paths, and memory results can all consume context. Output caps are inconsistent across tools.
6. **Error handling is broad.** Catch-all exception conversion keeps the agent alive but may hide programming errors that should fail tests or be surfaced distinctly.
7. **Runtime configuration is partly mutable and partly frozen.** This is workable, but new browser/desktop settings currently require restart and are not represented in `/status` or runtime state persistence.
8. **Startup has external side effects.** SearXNG startup can invoke Docker compose automatically. This is convenient but should be explicit in deployments where startup side effects are undesirable.
9. **The coder cannot ask questions.** Autonomous delegation is useful, but ambiguous tasks can lead to wrong edits. A structured “blocked / needs clarification” return path is safer than guessing.
10. **The model sees many tools at once.** A large catalog increases prompt size and tool-selection confusion. Capability-specific registries or deferred tool discovery would reduce this.

## 5. Syntax, logical, and theoretical review

### Syntax/type status

Focused tests passed after the additions. The initial type check identified and corrected missing registration imports and a test typing mismatch. The optional PyAutoGUI import is lazy and isolated so the base installation does not require it.

A full project verification should still be run after this report is written:

```bash
uv run pytest
uv run pyright
```

### Logical risks

- A successful tool result does not necessarily mean the desired real-world effect occurred. For example, a click can target the wrong matching element, a command can launch and immediately exit, or a workspace dispatch can be accepted but fail to produce the intended focus.
- The agent generally trusts tool output as observation, but it does not systematically perform postcondition checks. Desktop actions should return before/after state where possible.
- Browser actions are selector-driven rather than goal/postcondition-driven. “Clicked” is not equivalent to “the form was submitted successfully.”
- Unrestricted shell and persistent browser login state create a privilege boundary that is much larger than the model’s natural-language instructions.
- Model-produced JSON is validated structurally but not semantically. A valid dispatcher, URL, selector, path, or shell string may still be unsafe or irrelevant.

### Theoretical design improvements

1. **Capability security:** issue short-lived, per-turn capabilities for browser, desktop, filesystem, and shell rather than exposing all tools continuously.
2. **Policy engine:** evaluate an action against target, operation, risk, and user policy before execution.
3. **Plan/execute split:** have the model produce a plan, show or validate it, then execute atomic actions with postconditions.
4. **Typed action objects:** use dedicated dataclasses/enums for Hyprland operations, browser actions, paths, and coordinates rather than passing generic dictionaries deep into the system.
5. **Structured observations:** return normalized JSON for windows, workspaces, pages, accessibility nodes, and command results instead of raw text wherever possible.
6. **Provider-neutral telemetry:** add a response metadata object with measured input/output tokens, estimated tokens, context window, latency, retries, finish reason, and request id.
7. **Tool result budgets:** enforce byte/token limits per tool, per turn, and per provider request.
8. **External side-effect isolation:** run browser and desktop capabilities in a separate supervisor process with a narrow IPC protocol. This prevents a provider/model failure from directly owning the main process’s complete authority.

## 6. Request token and cost estimation

### Important limitation

The current code does **not** yet collect provider-reported usage in a normalized runtime telemetry record. The figures below are estimates for planning/cost comparison, not billing facts. This remains a follow-up item; the present implementation does not claim exact billing data.

The current compaction logic uses character length. A practical approximation is:

```text
estimated_tokens ≈ UTF-8/text characters ÷ 4
```

For compact English prose, 4 characters/token is often reasonable. For JSON, source code, tool schemas, non-English text, and token-heavy markup, the error can easily be 20–100% or more. Exact billing requires the provider’s tokenizer or provider-reported usage.

### What enters each model request

Every provider request generally includes:

1. The system prompt.
2. The registered tool schemas.
3. The retained conversation messages.
4. Retrieved memory embedded in the system prompt, when persistent memory is enabled.
5. Prior assistant tool-call payloads and tool results that survived compaction.
6. The current user message and any tool-result message from the preceding round.

Because the agent loops, one user turn can create several provider requests. The relevant cost is therefore:

```text
turn_input_tokens = sum(input_tokens for every model round in the turn)
turn_output_tokens = sum(output_tokens for every model round in the turn)
```

### Approximate request-size scenarios

These are planning estimates based on the current prompt/tool architecture, not live captures.

| Scenario | Typical serialized request size | Approx. input tokens/request | Notes |
|---|---:|---:|---|
| Simple chat, no tools used | 8–18 KB | 2k–4.5k | System prompt plus full tool catalog still enters the request. |
| Chat with memory block | 18–35 KB | 4.5k–9k | Depends on retrieved facts/history and prompt length. |
| One web search round | 25–50 KB | 6k–12.5k | Tool schemas plus search results/snippets. |
| One opened webpage round | 40–100 KB | 10k–25k | Page extraction can dominate the request. |
| Browser action after a snapshot | 40–110 KB | 10k–27.5k | Snapshot text plus browser schemas and history. |
| Desktop inspection/action round | 20–60 KB | 5k–15k | Hyprland JSON client/window output can be large. |
| Coding-agent round with source/tool output | 30–120 KB | 7.5k–30k | Highly dependent on files and command output. |
| Near compaction ceiling | up to ~80 KB by current heuristic | ~20k heuristic tokens | The 80k limit is characters, not provider tokens. |

### Tool schema overhead

The catalog is sent on every request through the provider call. The exact size varies with the current registry, but a rough planning estimate is:

- Core filesystem/shell/life/memory/web tools: approximately 2k–6k tokens.
- Adding browser tools: approximately 1.5k–3.5k tokens.
- Adding desktop tools: approximately 1.5k–4k tokens.
- A registry containing all current capabilities can therefore spend several thousand input tokens before the conversation itself is considered.

This is one of the clearest optimization opportunities: do not send browser and desktop schemas on turns that cannot need them.

### Cost calculation model

For a provider with input price `P_in` per million tokens and output price `P_out` per million tokens:

```text
estimated_cost = (input_tokens / 1_000_000 * P_in)
               + (output_tokens / 1_000_000 * P_out)
```

For multi-round tool use, calculate this per round and sum it. Do not count a tool call as a single request; the tool result causes another model request.

### Telemetry implementation recommendation

Although telemetry was not requested as a runtime feature in this change, it should be added next. A suitable normalized structure is:

```text
RequestTelemetry:
  timestamp
  agent: aria | coder | memory
  provider
  model
  request_id
  input_tokens_reported: int | null
  output_tokens_reported: int | null
  input_tokens_estimated: int
  output_tokens_estimated: int
  context_window_tokens: int | null
  serialized_input_chars: int
  serialized_output_chars: int
  tool_schema_chars: int
  message_count
  round_number
  latency_ms
  retries
  finish_reason
  error
```

Log the record with secrets redacted and aggregate counters in `/status`. Persist only low-sensitivity aggregates by default; raw prompts and tool outputs should not be stored in telemetry unless explicitly enabled.

## 7. Optimization priorities

### Highest impact

1. **Dynamic tool selection.** Keep a small base catalog and expose browser, desktop, web, memory, and coding tools only when relevant or explicitly requested.
2. **Token-aware compaction.** Replace character heuristics with provider/tokenizer-aware counting, or at least use separate conservative budgets for text, JSON, code, and tool schemas.
3. **Compact structured tool results.** Return summaries plus IDs and provide follow-up detail tools instead of injecting entire webpages, client lists, or shell outputs.
4. **Cache stable system/tool instructions.** Use provider prompt caching where available and avoid rebuilding/injecting duplicated memory content.
5. **Round minimization.** Combine independent read operations where safe and stop once postconditions are established.
6. **Per-tool output budgets.** Add hard byte and estimated-token limits to browser snapshots, web pages, shell output, memory search, and desktop JSON.

### Medium impact

1. Add exact model context-window metadata to provider configuration.
2. Add request latency and retry telemetry.
3. Summarize old tool results into durable memory rather than resending raw payloads.
4. Add a browser accessibility-tree observation mode with compact element IDs.
5. Return before/after desktop state for dispatches.
6. Avoid sending full tool schemas to the coder when it has no need for browser/desktop capabilities.
7. Add session-level token/cost dashboards to `/status` and exported reports.

### Lower impact but worthwhile

1. Rename “chain of thought” UI to “execution trace.”
2. Consolidate duplicated comments and repeated startup comments.
3. Replace generic `dict[str, Any]` tool arguments with typed validation helpers.
4. Add consistent machine-readable error codes.
5. Add lifecycle methods for all stateful services and close them in one supervisor.

## 8. Further development roadmap

### Phase 1 — reliability and observability

- Complete full pytest and Pyright verification.
- Add normalized provider usage/latency/context telemetry.
- Add live Chromium smoke tests behind an explicit opt-in marker.
- Add Hyprland smoke tests using a fake `hyprctl` executable and a real-session manual checklist.
- Add configuration validation tests for every browser/desktop field.
- Add regression tests for persistent browser shutdown and failed browser startup.

### Phase 2 — safety and policy

- Add a configurable confirmation/policy layer, even if disabled by default for trusted local use.
- Separate “navigation/read” from “mutation” browser capabilities.
- Add local URL policy, download/upload quotas, and sensitive-window warnings.
- Remove arbitrary `desktop_shell` from normal managed deployments.
- Restrict or separately disable the existing broad shell tool when computer-control mode is enabled.
- Add an emergency stop hotkey or process command that closes browser automation and stops desktop input.

### Phase 3 — better action quality

- Accessibility-tree browser observations with stable element references.
- Hyprland operations with typed window/workspace selectors and postcondition checks.
- Monitor-aware coordinates and backend capability detection.
- App process tracking and safe close semantics.
- Explicit popup/new-tab handling.
- Plan/execute workflow for multi-step computer tasks.

### Phase 4 — architecture scaling

- Supervisor process for browser/desktop authority.
- Capability-scoped registries.
- Provider adapter metadata and prompt caching.
- Storage-independent memory facade.
- Event-sourced action audit with redacted arguments and outcome state.

## 9. Configuration recommendations

For initial real-machine testing:

```yaml
browser:
  enabled: true
  headless: false
  profile_directory: data/browser-profile-aria

desktop:
  enabled: true
  mode: managed
  input_backend: arch
  launchers:
    terminal: [kitty]
    browser: [firefox]
```

Install and verify the local dependencies separately:

```bash
uv sync
uv run playwright install chromium
sudo pacman -S wtype ydotool grim
```

Do not initially enable unrestricted mode. If you later enable it, set an
explicit Hyprland configuration path and keep the profile separate from normal
browser data:

```yaml
desktop:
  mode: unrestricted
  hyprland_config_path: /home/USER/.config/hypr/hyprland.conf
```

The current no-prompt policy is a deliberate user choice, not a security
recommendation. The assistant should be treated as a local process with access
to logged-in browser accounts, screenshots, keyboard/mouse input, application
launch, window management, and—under unrestricted mode—arbitrary desktop shell
execution.

## 11. Final conclusion

The requested capabilities are now represented as explicit, configurable ARIA-only tools rather than being hidden behind ad hoc shell calls. The managed/unrestricted split is a meaningful improvement over exposing arbitrary desktop control by default, and Playwright provides a proper browser automation foundation. Proactive work, timers, notifications, LifeOS monitoring, local profile inference, workflow allowlists, and ephemeral multimodal input are also now wired into the same process with persistent scheduler state and audit records.

However, the system’s effective authority is determined by the union of all exposed tools, not only the new desktop module. Because ARIA already has a broad shell tool, persistent memory, browser credentials, and no confirmation prompts, the current design should be considered **trusted-user, attended-use software**. The next most valuable engineering step is normalized runtime telemetry plus dynamic capability/policy control; these will improve both cost decisions and safety without requiring another large feature expansion.
